## 三、本轮新发现问题

### 🟠 N-16-1(高危·功能性回归):后台写操作被 CSRF 全部拦截

- `admin/__init__.py` 中 `dashboard`、`health_page` 调用 `_make_csrf_response(..., username=admin)` 传了用户名,但 **`users_page`、`files_page`、`logs_page` 调用时漏传 `username`**。
- `_make_csrf_response(template, ctx, username="")` → `_get_csrf_token("")`,而 `_get_csrf_token` 开头 `if not username: return ""` → **返回空串**。于是这些页面渲染的表单 `csrf_token` 为空,同时 `set_cookie("csrf_token", "")` 把 cookie 覆盖为空。
- 用户在 /users 点「改会员/封禁」或在 /files 点「删除」提交 POST 时:`_verify_csrf(request, csrf_token="", username=admin)` 中 `cookie_token=""` → `if not cookie_token or not form_token: return False` → **抛 403「CSRF token 验证失败」**。
- 后果:后台所有状态变更操作(改会员等级、封禁/解封用户、删除文件)在当前代码下 **100% 失败**。这是 N-15-4 修复(令 `_get_csrf_token("")` 返回空)时漏改这三个页面调用点引入的回归。
- 建议:`users_page`/`files_page`/`logs_page` 的 `_make_csrf_response(...)` 补上 `username=admin`(与 dashboard 一致)。

### 🟡 N-16-2(中危·可靠性):影子复制游标在复制失败时仍无条件前进,导致影子频道永久漏消息

- `scheduler.replicate_all_active_to_shadows`:取 `new_messages` 后对每个 shadow 调 `_copy_messages`(内部对单条 `copy_message` 失败仅 `logger.warning` 后跳过),循环结束却执行 `latest_id = max(_get_msg_id(msg) for msg in new_messages)` 并 `self._cursor_cache[slot_id] = latest_id`。
- 即游标推进到本批 **所有** 抓取消息的最大 id,与「是否复制成功」无关。若某些消息 copy_message 因 FloodWait/网络/权限瞬时失败,它们被跳过,但下一周期 `min_id=latest_id` 不再抓取它们 → **影子频道永久缺失这些文件**,削弱「3×45 冗余」承诺。
- 建议:仅将游标推进到「已成功复制到全部 shadow」的最大连续 msg_id,或对失败消息记录待重试队列。

### 🟡 N-16-3(中危·补齐完整性):新频道存量补齐仅拉最新 200 条

- `auto_fill_new_channels` 通过 `_fetch_all_media(bot, active_channel, limit=200)` 获取存量,`iter_messages(limit=200)` 只取 **最新 200 条**;随后把 `last_synced_msg_id` 置为这 200 条的最大 id。
- 若 Active 频道历史媒体数 > 200,新影子只补齐最新 200 条,更早文件既不会被补齐(limit 截断),也不会被后续 replicate 回填(游标已指向最新)→ **大频道的新影子冗余不完整**。
- 建议:补齐时分页拉取全部历史(去掉 limit 或循环翻页),或将游标设为已补齐范围的下界以便后续增量继续。

### ⚪ N-16-4(低危·DR):恢复跳过 api_hash 致全新库无法 INSERT relay_accounts

- N-15-3 的修复对 relay_accounts 的 INSERT 也剔除了 `api_hash` 列;但 CRDB `relay_accounts.api_hash` 为 `TEXT NOT NULL`。全新库(无同 pk 冲突)执行 INSERT 时缺该列 → NOT NULL 违例 → 该行被 `except` 记错跳过。
- 影响有限:中继账号权威源为本地 relay_pool.db,CRDB 仅备份;但严格意义上「从 CRDB 全量恢复 relay_accounts」在全新库仍不可用。建议恢复时对新行填占位或明确文档化「relay_accounts 从本地 SQLite 恢复」。

### ⚪ N-16-5(低危/说明):H2 多 worker 覆盖 & get_updates 回退

- `admin` 的 CSRF/登录失败仍是「整字典 JSON 写单个 SQLite 键」,多 worker 会后写覆盖前写;当前单 worker 部署无影响,横向扩容前需改条目级或用 CRDB。
- `scheduler._fetch_new_messages` 在 Telethon 不可用时回退 `get_updates(offset=-100)`,仅兜底且有 warning 日志,长期不可用时建议升级为告警。
