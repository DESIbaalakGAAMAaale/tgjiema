## 三、本轮新发现问题

### 🟡 N-15-1(中危·安全):备份脱敏对「行级」密钥无效,R2/密钥仍可能明文落盘

- `services/db_backup.py` 的 `_redact_secrets` 只按「列名」匹配 `_SENSITIVE_FIELDS`(r2_secret_key/r2_access_key/api_hash),且仅对 backup_config、relay_accounts 两表生效。
- 但 R2 凭证在本项目里是以「行」形式存于 `backup_config`/`kv_config`(config_key='r2_secret_key', config_value=<明文密钥>),列名是 config_key/config_value,**不匹配** `_SENSITIVE_FIELDS`,因此不会被脱敏;`kv_config` 甚至不在脱敏目标表内。
- 后果:若管理员曾通过后台把 R2 凭证写入配置表,备份 JSON 上传到 R2 时这些密钥会以明文导出。
- 建议:脱敏逻辑改为对 backup_config/kv_config 按 config_key 命中敏感键名时对 config_value 打码;并把 kv_config 纳入脱敏范围。

### 🟡 N-15-2(中危·灾备完整性):message_backups 未纳入备份,DR 恢复后影子投递会 404

- `db_backup.BACKUP_TABLES = SMALL_TABLES`,不含 `message_backups`(它在 `_LARGE_TABLES` 中,被排除)。
- 而 `db_restore.ALL_TABLES` 却列了 message_backups —— 备份从不写、恢复自然拿不到(空操作)。
- message_backups 是「主频道 msg_id → 影子频道 msg_id」映射,是故障切换时影子投递不 404 的关键,且无法像 file_records 那样从 Telegram 简单重建(需重新触发 Mon 复制才会重生成)。
- 后果:从备份重建 CRDB 后,一段时间内所有走影子频道的降级投递会 404,直到 Mon 重新复制补齐映射,削弱了「冗余」承诺的可用性。
- 建议:将 message_backups 纳入备份(可单独分片/限行),或在 DR 文档中明确「恢复后需等待 Mon 重建映射」。

### 🟡 N-15-3(中危·灾备):relay_accounts 脱敏后恢复不可解密

- `_redact_secrets` 会把 relay_accounts 的 api_hash 列替换为 `***REDACTED***`。
- `db_restore` 恢复 relay_accounts 时会把 `***REDACTED***` 原样写回 CRDB;而 `relay_db.decrypt()`(PRE-10)对非法密文直接抛 RuntimeError。
- 后果:全新 VPS 若本地 relay_pool.db 为空并从 CRDB 恢复,`get_active_accounts` 解密会抛错,中继账号需人工重新录入。
- 说明:中继账号权威源是本地 relay_pool.db(未纳入此备份),故实际影响有限,但属 DR 缺口,建议在恢复流程中跳过 relay_accounts 的 api_hash 列或标注需重新录入。

## 四、低危/质量项

- ⚪ **N-15-4 CSRF 非按会话绑定**:`admin._verify_csrf` 用 `cookie_token in _csrf_tokens.values()` 判定,即任一已注册 token 均可通过,未与当前登录用户强绑定。单管理员场景影响很小,建议改为按 username 精确比对。
- ⚪ **N-15-5 H2 多 worker 覆盖**:CSRF/登录失败持久化是把整字典 JSON 写入同一 SQLite 键,多 worker 会「后写覆盖前写」。当前单 worker 无影响,扩 worker 前需改为条目级读改写或用 CRDB。
- ⚪ **N-15-6 relay_[instance.is](http://instance.is)_busy 边缘泄漏**:`send_external_code` 置 is_busy=True 后,其复位依赖 `_message_loop` 的 finally 且仅当 exchange 已清理时才复位;某些异常/清理时序下可能残留 busy,导致该账号后续拒绝请求。建议在 exchange 结束路径统一确保 is_busy 复位。
- ⚪ **N-15-7 get_updates 回退路径**:scheduler._fetch_new_messages 在 Telethon 不可用时回退 `bot_instance.get_updates(offset=-100)`,仅能拿到最近少量更新且可能与其他轮询语义冲突;属兜底路径,建议在 Telethon 长期不可用时告警而非静默降级。
