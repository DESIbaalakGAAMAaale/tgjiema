## 三、本轮新发现（仅针对 H2 新代码，均为低危/提示）

- **N-14-1（提示，仅多 worker 场景）**：H2 的持久化是把整个 <code>_csrf_tokens</code> / <code>_login_failures</code> 字典序列化为 JSON 写入同一 SQLite 键。当前部署为单进程 uvicorn，重启恢复已完全生效；但若未来扩多 worker，多进程各自把本进程字典整体回写会“后写覆盖前写”（丢失其他 worker 新增的 token/计数）。单 worker 下无影响。
- **N-14-2（提示）**：持久化走 <code>asyncio.ensure_future(*persist*...)</code> fire-and-forget，写 SQLite 与抛出 HTTPException 存在极小竞争窗口（登录失败后立即崩溃且持久化未完成时，该次失败计数可能未落盘），属可接受范围。
- **N-14-3（说明，非缺陷）**：<code>_count_cache</code>（用户/文件/日志列表总数的 60s TTL 缓存）仍为纯进程内内存，未持久化。因其仅为性能缓存、非安全相关、且 60s 自动重建，保持现状合理，无需修改。

## 四、优先级建议

1. **N-13-2**：下轮重新确认 <code>user_[relay.py](http://relay.py)</code>；若 <code>UserRelay</code> 死代码仍在，删除或合并到 <code>RelayInstance</code>。
2. **N-14-1（仅当计划扩 worker 时）**：若未来后台要上多 worker，把限流/CSRF 改为按条目级读改写（而非整字典覆盖）或直接用 CRDB。单 worker 下可不动。
