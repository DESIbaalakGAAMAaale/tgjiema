## 二、🔴 严重问题

### R29-1 🔴 媒体过滤改动使「文字错误」与「翻页按钮」检测双双失效

新的 `on_new_message` 只把"媒体消息"放入 `events`，纯文本（含带按钮的文本）改放 `text_responses`：

```python
msg = event.message
if msg.media and not isinstance(msg.media, MessageMediaWebPage):
    exchange.setdefault("events", []).append(event)      # 只有媒体进 events
else:
    text = getattr(msg, "message", None) or ""
    if text:
        exchange.setdefault("text_responses", []).append({"msg_id": msg.id, "text": text})
# 另外：有 reply_markup 时 exchange["_keyboard_msg"] = event.message
```

但决策函数 `_make_decision` 的**错误检测和按钮检测仍然只遍历 `events`**：

```python
msg_events = exchange.get("events", [])
if not msg_events:
    return {"action": "finish", ..., "reason": "无消息"}
for ev in msg_events:                       # ← 只扫 events
    text = (getattr(ev.message, "message", None) or "").lower()
    for ek in _ERROR_KW: ...                 # 文字错误检测
for ev in msg_events:                       # ← 只扫 events
    if not (msg.reply_markup and ...): continue   # 翻页/文件按钮检测
```

**关键佐证（说明这是无意的迁移遗漏）：** 作者已经把"限速检测"迁移到了 `text_responses[-5:]`（`_check_rate_limit`），却**漏迁了错误检测与按钮检测**，三者本应一致。

**后果（目标 Bot 用"纯文本+内联键盘"呈现文件列表/分页时——这是 Telegram 网盘码 Bot 极常见形态）：**

- 键盘挂在文本消息上 → 不进 `events` → `_make_decision` 看不到按钮（它从不读 `_keyboard_msg`）→ 直接 `finish`「无翻页按钮」→ **只收到首屏，后续分页文件全部丢失（静默漏投）**。
- 若媒体尚未到达而先来文本+键盘 → `msg_events` 为空 → 立即 `finish`「无消息」→ **一个文件都收不到**。
- 文字型错误（"已过期/未找到/not found"）在文本里 → 不进 events → 不触发 `error` → 用户拿到静默空结果而非明确报错。

> 注：若目标 Bot 把键盘挂在"媒体"消息上，则检测仍正常。因此影响面取决于目标 Bot 形态，但代码相对上一版**客观是回退**（旧版所有消息都进 events）。
> 

**修复建议（任选其一）：**

1. `on_new_message` 中，**凡带 `reply_markup` 的消息一律也 append 到 `events`**（媒体过滤只用于"是否算文件"，不应影响决策可见性）；或
2. `_make_decision` 的错误检测改为同时扫描 `text_responses`，按钮检测改为消费 `_keyboard_msg`（并保留 `events` 内媒体键盘）。

### R29-2 🔴 `mark_code_mapped` 只在「取消/失败」路径触发，成功路径反而不缓存 → 失败码被永久毒化、后续静默漏投

`_message_loop` 的 `finally`：

```python
finally:
    self.is_busy = False
    if bot_username in self._bot_exchange:        # ← 仅当 exchange 未被 pop 时
        exchange = self._bot_exchange[bot_username]
        ...
        await relay_db.mark_code_mapped(exchange.get("code", ""))
```

各退出路径是否已 pop：

- `action=="finish"` → `_process_all_collected()` **会 pop** → finally 时不在字典 → **不标记**
- `action=="error"` → `_cleanup_exchange()`（`self._bot_exchange.pop(...)`）**会 pop** → **不标记**
- `except Exception` → `_process_all_collected()` **会 pop** → **不标记**
- `except asyncio.CancelledError: pass` → **不 pop** → finally 时仍在字典 → **标记！**

而 `_do_send_external_code` 开头：

```python
if relay_db and await relay_db.is_code_mapped(code):
    logger.info("码已映射（本地缓存），跳过")
    return True          # ← 静默"成功"，不再投递
```

**问题（逻辑正好相反）：**

1. **成功映射不会被缓存**（finish 先 pop）→ 号称"避免重复查 CRDB"的优化**根本不生效**。
2. **取消/失败才会被缓存**。`_restart_settle` 每来一条新消息就取消上一个 settle 任务 → 采集途中就会走 CancelledError → **在采集尚未完成时就把码标记为已映射**；若这次最终入库失败，则该码被永久标记。
3. 之后任何人再请求同一个码 → `is_code_mapped` 为真 → `return True` → **静默"成功"但根本没投递文件**。
4. `unmark_code(code)` 已定义，但**全仓没有任何调用点**，失败无法自愈。
5. `mapped_codes` 表**无 TTL/清理**（`cleanup_cooldowns` 只清 `bot_cooldown`）→ 毒化条目永久残留、单调增长。
6. `mark_code_mapped(exchange.get("code", ""))` 在 code 为空时会插入空串主键行（`INSERT OR IGNORE`，无害但不严谨）。

**修复建议：**

- 从 `finally` 移除 `mark_code_mapped`；改为**在 `_process_all_collected` 确认入库成功（收到 idx "已就绪"确认）后**再标记。
- 失败/超时路径调用 `unmark_code(code)`。
- 给 `mapped_codes` 加基于 `created_at` 的 TTL 清理任务。
- 标记前判空：`if code: await relay_db.mark_code_mapped(code)`。

## 三、🟠 高

### R29-3 🟠 URL 按钮触发对「不可信实体」自动 `/start`（类 SSRF/被诱导交互）

`_click_button` 处理 URL 按钮时，会解析按钮里的 `t.me` 链接并主动向该实体发送 `/start`：

```python
if "t.me/" in url or "telegram.me/" in url:
    parsed = urlparse(url); start_param = parse_qs(parsed.query).get("start", [None])[0]
    if start_param:
        entity = await self._client.get_entity(parsed.path.strip("/"))
        await self._client.send_message(entity, f"/start {start_param}")
```

按钮内容来自**目标 Bot（不可信）**。恶意目标可放置指向 `t.me/attacker_bot?start=…` 的按钮，诱导中继账号自动向攻击者控制的 Bot 发 `/start`（可用于探测/关联/骚扰中继真实账号）。**建议：对可跳转实体做用户名白名单/黑名单，或默认禁用 URL 按钮自动跳转。**
