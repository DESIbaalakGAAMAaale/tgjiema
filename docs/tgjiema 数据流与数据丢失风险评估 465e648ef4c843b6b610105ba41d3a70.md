# tgjiema 数据流与数据丢失风险评估

<aside>
⚠️

基于仓库 `maxiuquan/tgjiema` 当前 HEAD（commit `3274f37`）的源码审查。核心结论：文件本体冗余较强，但**取件映射（codes/file_records）无外部备份**是最大软肋。

</aside>

## 一、整体流程

### 1. 上传链路（文件进入系统）

流向：用户 → Up Bot → Active 频道 → pending_uploads → Idx Bot → 返回取件码

1. 用户把文件发给 **Up Bot**。
2. Up Bot 用 round-robin 选一个 Active 存储频道，`copy_message` 把文件存进【只 1 个】Active 频道。
3. 写一行 `pending_uploads`，并通知 Idx Bot。
4. **Idx Bot** 消费 `pending_uploads` → `code_generator` 生成文件码 → 写 `file_records` + `codes`（CRDB）→ 把取件码返回给用户。

<aside>
⚠️

上传完成那一刻，文件本体**只存在于 1 个 Active 频道**，副本还没生成。

</aside>

### 2. 冗余复制链路（Mon Bot 后台异步，约 30s/次）

1. 检测 5+ Bot 心跳。
2. `replicate_all_active_to_shadows()`：把 Active 新消息复制到 Shadow1 / Shadow2。
3. `auto_fill_new_channels()`：新频道补齐存量文件。
4. `_check_rotation()`：环形轮转 + 降级/提升，更新 `cells.status` / `demoted_to_channel_id`。

<aside>
💡

「1 组 × 3 槽 = 3 副本」的冗余是 Mon Bot **事后异步补出来的，不是上传时同步写的**。

</aside>

### 3. 取件链路（用户下载）

流向：用户输入取件码 → Idx Bot 解码并写 `jobs` 队列 → Dsp Bot 轮询 `jobs` → 发给用户

- Dsp Bot 通过 `delivery_resolver.resolve_delivery_channel()` 解析发送频道：
    - Active → 直接发；
    - 有 `demoted_to` → 跳到接替频道；
    - Shadow / lost → 沿环形找下一个可用频道（最多 3 层降级）。
- 最终由 **Dsp Bot（唯一出口）** `copy_message` 发给用户。

<aside>
📮

**R100 是只写入的永久归档频道**：只接收写入，不参与任何读取/派发，也不并入环形拓扑。所以正常取件链路不会从 R100 读。
⚠️ 代码待核对：`delivery_resolver.py` 目前在 `resolve_delivery_channel()` 和 `_walk_ring_for_channel()` 里仍把 `r100` 列为可派发状态（`status in ("active", "r100", ...)`）。只要没有 `codes.primary_channel_id` 指向 R100、且环形 `next_active_chat_id` 不指向它，这条分支就走不到；但为与设计一致，建议从可派发状态列表中移除 `r100`。

</aside>

### 4. 备份链路

`db_backup.py` 每 360 分钟只把「小表」备份到 R2：

- ✅ 备份：`cells`、`users`、`spare_pool`、`backup_config`、`relay_accounts`、`code_bot_mapping`、`kv_config` 等。
- ❌ 不备份：`codes`、`file_records`、`jobs`、`decode_logs`、`pending_uploads`、`message_backups`。

## 二、数据丢失风险清单

正常运行不会丢；但存在以下特定场景，按严重程度排序。

### 🔴 高 — codes / file_records 没有外部备份

`db_backup.py` 明确只备份 `SMALL_TABLES`，排除了 `codes`、`file_records`，注释理由是「可从 Telegram 频道重新索引」。

问题：

- `db_restore.py` 的恢复列表里列了 `codes`/`file_records`，但备份里根本没有，恢复只会是空的；
- 仓库里看不到「从频道重新索引」的实现，那句注释目前只是设想。

**后果**：一旦 CockroachDB 数据丢失/误删/逻辑损坏，所有取件码 → 频道/消息 的映射永久消失。文件字节还在 Telegram 频道里，但再也解不出来。CRDB 自身多副本、日常安全，但「无外部备份」= 映射关系的单一逻辑故障点。

### 🟠 中 — 上传后到复制前的「单副本窗口」

上传时文件只进 1 个 Active 频道，副本靠 Mon Bot 下一轮（约 30s 级）异步补。若该账号恰好在复制完成前被封，文件只剩这一份且随账号消失 → 丢失。

### 🟠 中 — Mon Bot 长时间宕机

Mon 是复制/轮转/降级的唯一执行者。它挂了不会立刻丢数据，但新文件会持续单副本、冗余形同虚设；此时再叠加封号就会丢。属关键单点。

### 🟡 低 — TTL 到期（预期删除）

`file_ttl_days > 0` 会写 `expire_time`，到期标记 expired/deleted。注意 `up_bot` 中用户选 0 时会回落到 `settings.DEFAULT_FILE_TTL_DAYS`；若该默认值配成非 0，用户以为「永久」的文件会被悄悄过期。务必确认 `.env` 中该值 = 0。

### 🟡 低 — pending_uploads 孤儿

文件已 copy 进频道、但 idx_bot 写 `file_records`/`codes` 前崩溃 → 文件在频道里但没有取件码。`pending_uploads` 也不在备份范围。需确认 idx_bot 对 `pending_uploads` 有幂等重放。

---

## 三、修复建议（按优先级）

- [ ]  **【必做】** 让 `codes`/`file_records` 有可恢复的备份路径：纳入 R2 备份（增量/分页导出规避 RU），或真正实现「扫描频道重建索引」脚本，二选一必须落地。
- [ ]  **【应做】** 上传时同步写 ≥2 个槽再返回取件码，或返回码时标注「冗余生成中」，并给 Mon 复制失败加重试与告警。
- [ ]  **【应做】** 把 Mon Bot 纳入 `/health` 强监控，确认其崩溃能被 `run_all.py` 捕获并自动重启。
- [ ]  **【核对】** 确认 `.env` 中 `DEFAULT_FILE_TTL_DAYS = 0`（永久有效）。
- [ ]  **【核对】** 确认 idx_bot 对 `pending_uploads` 有幂等重放，避免孤儿文件。

---

## 四、一句话总结

- **文件本体**：靠 3 槽 + R100 冗余，抗单账号封禁能力强 —— 但有「上传后短暂单副本窗口」和「Mon 宕机则不再冗余」两个前提。
- **取件映射（codes/file_records）**：真正的软肋 —— 没有外部备份、也没有重建索引工具，CRDB 一旦逻辑性丢数据就是不可逆的取件能力丢失。

<aside>
📌

最该先补的一件事：让 `codes`/`file_records` 有可恢复的备份路径。这一项补上后，这套架构才算真正「不丢数据」。

</aside>
