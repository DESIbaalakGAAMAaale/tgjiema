# 频道冗余环 · 副本重建方案(Manifest 驱动,免中继账号)

<aside>
🛠️

**目标**:45 个存储频道组成一个冗余环,某个失效时新建频道补位。让补位频道能自动追齐环内已有的全部内容,**不需要每次拉一个中继用户账号进频道读历史**。

</aside>

## 一、问题与根因

- **Bot 读不了历史**是 Telegram 硬限制:Bot API 无 `getHistory`,即使用 MTProto 拿 bot token,`messages.getHistory` 对 bot 身份也是禁用的。只有**用户账号 + 频道成员**才能拉历史。
- **真正的错误在于数据源选错**:把"Telegram 频道历史"当成重建副本的数据源,所以每次补位都被迫拉中继账号。
- **关键事实**:Bot 虽然不能枚举历史,但**能按已知 `message_id` 直接 `copyMessages` / `forwardMessages`**——只要它是源频道的成员/admin,不需 `getHistory` 就能按 ID 把消息复制到新频道。缺的只是"它不知道有哪些 ID"。

<aside>
💡

**核心思路**:重建副本靠"**清单(manifest) + 写入**",不靠"读历史"。自己维护一份消息清单(相当于写前日志 WAL),补位时 bot 按清单从存活 peer 复制。读历史退化成"建索引那一次"。

</aside>

## 二、总体架构

| 需求 | 用谁 | 是否需要用户账号入频道 |
| --- | --- | --- |
| 环内新消息实时入索引 | Mon Bot(admin,实时 update) | 否 |
| 补位频道重建 | Mon Bot 按 manifest 从 peer `copyMessages` | 否 |

## 三、Manifest 表结构

一条记录 = 环内一个逻辑文件(按 `file_unique_id` 去重),并记录它在每个频道的 `message_id`。

```sql
-- 逻辑文件主表(环级去重)
CREATE TABLE ring_object (
  ring_id        TEXT    NOT NULL,
  file_unique_id TEXT    NOT NULL,   -- 跨 bot 稳定,去重键
  checksum       TEXT,               -- 可选:下载后算 sha256,验证一致性
  media_type     TEXT,               -- document/photo/video/...
  size_bytes     BIGINT,
  caption        TEXT,
  first_seen_at  TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (ring_id, file_unique_id)
);

-- 每个副本在各频道的实例(同一文件在不同频道 message_id 不同)
CREATE TABLE channel_copy (
  ring_id        TEXT    NOT NULL,
  file_unique_id TEXT    NOT NULL,
  channel_id     BIGINT  NOT NULL,   -- 频道(-100... 形式)
  message_id     BIGINT  NOT NULL,   -- 该文件在该频道的消息 ID
  file_id        TEXT,               -- per-bot,仅当前 bot 可用,仅作缓存
  status         TEXT DEFAULT 'ok',  -- ok / missing / failed
  synced_at      TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (ring_id, file_unique_id, channel_id),
  FOREIGN KEY (ring_id, file_unique_id)
    REFERENCES ring_object(ring_id, file_unique_id)
);
CREATE INDEX ix_channel_copy_chan ON channel_copy(channel_id, status);
```

<aside>
⚠️

**去重键用 `file_unique_id`,不要用 `file_id`**。`file_id` 是 per-bot / 可变的,换个 bot 就失效;`file_unique_id` 跨 bot 稳定,才能保证幂等去重。

</aside>

## 四、实时维护 manifest(bot 常驻)

Mon Bot 作为环内所有频道的 admin,每收到一条带文件的新消息就登记:

```python
async def on_channel_post(msg):
    media = extract_media(msg)          # document/photo/video...
    if not media:
        return
    fuid = media.file_unique_id
    # 1) 主表 upsert(环级去重)
    upsert_ring_object(RING_ID, fuid,
                       media_type=media.type, size_bytes=media.size,
                       caption=msg.caption)
    # 2) 登记该频道的副本实例
    upsert_channel_copy(RING_ID, fuid,
                        channel_id=msg.chat.id,
                        message_id=msg.message_id,
                        file_id=media.file_id, status='ok')
```

> 从这一刻起,环内新增内容永远不需要再读历史。
> 

## 五、补位频道重建(bot 只写不读)

某频道失效 → 新建 `new_channel` 并把 Mon Bot 加为 admin → 跑重建任务:

```python
async def rebuild_channel(ring_id, new_channel_id, batch=30, sleep_s=1.0):
    # 逐个逻辑文件:要求在 new_channel 已存在一份副本
    todo = query_missing_in_channel(ring_id, new_channel_id)
    for chunk in chunked(todo, batch):
        src_ids, dst_map = [], []
        for fuid in chunk:
            # 幂等:已在新频道就跳过(断点续传)
            if exists_copy(ring_id, fuid, new_channel_id):
                continue
            # 从任一存活 peer 取该文件的 (channel_id, message_id)
            src = pick_healthy_peer_copy(ring_id, fuid,
                                         exclude=new_channel_id)
            if not src:
                mark(ring_id, fuid, new_channel_id, 'missing')  # 全环都没 → 真丢失
                continue
            src_ids.append((src.channel_id, src.message_id, fuid))
        # 按源频道分组 copyMessages(bot 在源频道是成员即可,无需 getHistory)
        for from_chat, items in group_by_channel(src_ids):
            mids = [m for (_c, m, _f) in items]
            try:
                res = await bot.copy_messages(
                    chat_id=new_channel_id,
                    from_chat_id=from_chat,
                    message_ids=mids)          # 批量,不带转发尾巴
                for (_c, _m, fuid), sent in zip(items, res):
                    upsert_channel_copy(ring_id, fuid, new_channel_id,
                                        sent.message_id, status='ok')
            except FloodWait as e:
                await asyncio.sleep(e.value + 1)  # 退避重试
                # 本批下轮重跑(幂等,安全)
        await asyncio.sleep(sleep_s)             # 常规限流
```

**要点**

- **幂等可续传**:每步先查 `exists_copy`,失败重跑不会重复写入。
- **`copyMessages` vs `forwardMessages`**:冗余存储用 `copy`(不带"转发自"尾巴,副本干净);需保留来源则用 `forward`。
- **限流**:批量 20–30 条/轮 + 固定 `sleep`;遇 `FloodWait` 按返回秒数退避。
- **真丢失检测**:若全环都无该 `file_unique_id`(`pick_healthy_peer_copy` 为空),标 `missing` 告警——这才是真正的数据丢失。

## 六、与现状对比

|  | 现在(读历史) | 优化后(清单重建) |
| --- | --- | --- |
| 补一个新频道 | 拉中继账号进去读 history | bot 按 manifest 从 peer `copyMessages` |
| 是否需用户账号 | 每次都要 | 仅首次建索引一次 |
| 幂等 / 断点续传 | 难 | `file_unique_id` 去重,天然幂等 |
| 与 relay_pool 耦合 | 蹭它的 session | 完全解耦 |

<aside>
✅

**一句话**:给这个环建一份 `file_unique_id + 各频道 message_id` 的 manifest,由 bot 实时维护;补位时 bot 按 manifest 从存活 peer 复制。读历史只在"首次建索引"那一次,之后新增频道纯 bot 写入,不再需要任何中继账号入场。

</aside>
