## 三、本轮新发现问题

### 🟠 R30-1(疑似严重·待核实):`storage/r2.py` 的 `base_url` 疑似含字面双花括号,会让 R2 备份/恢复全线失效

源码读到的是:

```python
@property
def base_url(self) -> str:
    return f"{{https://{self._endpoint}}}/{self._bucket}"
```

在 Python f-string 中 `{{`→字面 `{`、`}}`→字面 `}`,该表达式会求值为 `{https://<endpoint>}/<bucket>`(带字面花括号),而非合法 URL `https://<endpoint>/<bucket>`。`upload/download/list_objects/delete` 全部基于 `base_url` 拼 URL,一旦如此,**所有 R2 操作都会因 URL 非法而抛错**。

- **为什么 28 轮没暴露**:`DB_BACKUP_ENABLED` 默认 `False`(PRE-07),测试时基本不会走 R2,故潜伏至今。
- **置信度说明(诚实)**:同文件其它 f-string(如 `f"{self.base_url}/{key}"`)读出来都是正常单花括号,唯独这一行是双花括号,倾向判断是**源码里真实写错**而非展示层伪影;但我无法在此执行 Python 100% 确认。
- **请务必在本机核实**:`python -c "from storage import r2; r2.get_r2().configure('acc','ak','sk','bkt'); print(repr(r2.get_r2().base_url))"`。若打印出带 `{` `}` 的字符串即为真实 bug,改成 `return f"https://{self._endpoint}/{self._bucket}"`。

### 🟠 R30-2:`bot_override` 匹配循环缺 `break`,最长前缀匹配语义被破坏(R29-8 引入)

`_do_send_external_code` 内联的覆盖匹配:

```python
for ov in self._bot_override_cache:
    if ov.get("is_active") and code.startswith(ov["prefix"]):
        bot_username = ov["bot_username"]   # 没有 break
```

`list_bot_overrides` 是 `ORDER BY length(prefix) DESC`(最长在前),原 `get_bot_override` 命中**第一个即返回=最长前缀**。现在没有 break,循环会被后续更短前缀覆盖,**最终生效的是最短前缀**——与"最长前缀匹配"完全相反。

- **触发条件**:配置了相互重叠的前缀(如 `AB` 与 `ABC`)时,外部码会被路由到错误的 bot → 解码失败。非重叠前缀不受影响。
- **修复**:命中后 `break`(或恢复调用 `get_bot_override` 的"首个即返回"语义)。

### 🟠 R30-3(待核实):Up Bot 的 `EXTERNAL_RELAY:` 入口在权限/限速校验之前,疑似缺少发送者身份校验

caption = update.message.caption or ""
if caption.startswith("EXTERNAL_RELAY:"):

### 🟡 R30-4:R29-3 白名单排除了"当前目标 bot",且用户名默认空串

- 白名单是 `{DECODER_BOT_USERNAME, UPLOAD_BOT_USERNAME}`,**不含当前正在交互的目标文件 bot `bot_username`**。若某些外部 bot 用 URL 深链按钮([t.me/该bot?start=…)做翻页/取件,点击会被判为越权而](http://t.me/该bot?start=…)做翻页/取件,点击会被判为越权而) `return False`,可能漏取文件。建议把当前 `bot_username` 一并纳入白名单。
- [settings.py](http://settings.py) 已确认 `UPLOAD_BOT_USERNAME/DECODER_BOT_USERNAME/SENDER_BOT_USERNAME` 三者**均已定义**(不会 AttributeError),但**默认值都是空串 `""`**;若 `.env` 未填,白名单退化为 `{""}`→所有 URL 按钮被拒。部署清单需强制填写这三个用户名。

### 🟡 R30-5(待核实):relay 的 ready_event 确认链路可能与 idx 的实际通知目标不一致

relay `_process_all_collected` 发 EXTERNAL_DONE 后等 120s,靠 `on_new_message` 收到"来自 decoder bot、含 code、含'已就绪/ready'"的消息来 `ev.set()`。但 idx 侧 `[Idx][poll]` 的"外部文件 {ext_code} 已就绪…"是发给 **`uploader_id`(原始用户)**、经 idx_bot 发出的,并非发给中继账号、且并非 decoder bot 发出。若二者确实不在同一通道,relay 的 120s 等待会必然超时→`_unmark_code`,而文件实际已由 idx poll 正常入库映射。

- **影响**:功能上文件仍能投递(靠 idx poll 兜底),但 relay 每次都白等 120s 并做一次"标记→反标记"的无效簿记;若某处依赖 mapped_codes 幂等,可能反复触发。
- **诚实说明**:我未取到 idx_bot 完整的"谁发确认给谁"逻辑,无法断言这是 bug,列为待核实。请在联调时确认:relay 账号是否真能在 120s 内收到 decoder→relay 的"已就绪+code"消息。

### 🟢 R30-6:webpage 预览消息仍会进入 `_download_and_cache_one` 尝试 `send_file`

R29-1 的 media 过滤只作用于"是否进 events",未作用于上传路径。webpage 预览(`MessageMediaWebPage`)`getattr(msg,"media")` 为真,会进入 `_download_and_cache_one` 尝试 `send_file`→大概率抛错被 catch→计数 `_decrement`。无数据损坏,仅有一次失败尝试与日志噪音。建议 `_download_and_cache_one` 内同样排除 webpage 预览。

### 🟢 R30-7:admin cookie `secure=True` 在 `http://127.0.0.1` 默认部署下的取值坑

CSRF cookie 设了 `secure=True, samesite="strict", httponly=True`(安全,✅)。但默认 `ADMIN_WEB_HOST=127.0.0.1` 若以纯 http 访问,部分浏览器对 `Secure` cookie 的存取行为不一致,可能导致 cookie 不回传→所有 POST 报"CSRF 验证失败"。现代 Chrome 对 [localhost](http://localhost) 视为安全上下文一般可用,但建议部署文档明确"经 HTTPS 反代访问",或本地调试放宽。
