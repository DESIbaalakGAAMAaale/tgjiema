## 二、🔴 严重（必须修复）

### 🔴 R31-1　R2 `base_url` f-string 花括号转义写错，导致 URL 非法、整个备份/恢复子系统不可用

**文件**：`storage/r2.py` → `base_url` 属性。

**问题代码**：

<aside>
🐛

`return f"{{https://{self._endpoint}}}/{self._bucket}"`

</aside>

**根因**：Python f-string 中 `{{` 会被转义成字面量 `{`、`}}` 会被转义成字面量 `}`。因此该表达式实际返回：

<aside>
❌

`{https://xxx.r2.cloudflarestorage.com}/bucket`（带一对字面花括号的非法 URL）

</aside>

httpx 无法解析这种 URL，导致 R2 的 `upload / download / list_objects / delete` **全部失败**。

**影响面**：SigV4 签名本身是正确的（host 用 `self._endpoint`、路径用 `canonical_uri`），只有实际请求 URL 被写坏。当前 `DB_BACKUP_ENABLED` 默认 `False`，备份与恢复默认关闭，所以线上暂时看不到爆炸——**但只要有人在 Admin Bot 里把 DB 自动备份打开（/set_db_backup on），整个备份/恢复立刻全线失效**，且属于「以为有备份、其实一条都没备成」的高危静默失败。

**修复**（去掉多余的双花括号）：

<aside>
✅

`return f"https://{self._endpoint}/{self._bucket}"`

</aside>

**建议**：修复后加一个最小自检——启动或开启备份时对 `base_url` 做一次 `httpx.URL(...)` 解析校验，解析失败直接 fail-fast 并告警，避免再次出现「静默失败型」备份。

## 三、🟡 待核实（需你在运行环境确认）

### 🟡 R31-2　中继验证码提交的配置键名疑似不一致 / phone 缺失

**文件**：`bots/admin_bot/conversation.py`（`relay_code:code` 状态）与 `bots/admin_bot/callback.py`（`action:relay_pending`）。

- 提交验证码时写入的是**带手机号的键**：`relay_auth_code:{phone}` 和 `relay_auth_pending:{phone}`，其中 `phone = context.user_data.get("relay_phone", "")`。
- 但交互入口 `interactive:relay_code` 只设置了会话状态，**没有在 user_data 里写入 `relay_phone`**。若管理员是直接点「🔑 提交验证码」按钮进入，`phone` 会是空串，于是写成 `relay_auth_code:`（空手机号键）。
- 同时 `action:relay_pending` 读取的是**不带手机号的全局键** `relay_auth_pending`，与写入的 `relay_auth_pending:{phone}` 也不是同一个键。

**风险**：多账号中继场景下，验证码可能写到错误/空的键，导致 `relay_instance` 读不到验证码、登录卡在等待验证码。**请核实 `relay_instance` 到底按哪个键读取验证码**（若它按 `relay_auth_code:{phone}` 读，则单账号且 phone 恰好为空时才不炸；多账号必炸）。

### 🟡 R31-3（沿用 R30-5）　外部码「已就绪」通知闭环需运行时确认

本轮已在 `idx_bot.handle_relay_delivery` 看到：`RELAY_BATCH/RELAY_DELIVER` 会向用户发「您请求的文件 {code} 已就绪，正在发送，请查收」，`relay_instance` 侧按 `DECODER_BOT_USERNAME` 消息中的「已就绪 / ready」做检测。**逻辑是通的**，但整条链路（解码机器人回发 → 中继账号识别 → 触发上传）仍依赖真实 Telegram 账号运行时行为，建议用一条真实外部码端到端验证。
