## 四、🔴 阻断级问题（必须修复）

<callout icon="🔴">**BLOCKER-1 · `storage/r2.py` `base_url` 双花括号仍未修（跨 4+ 轮未解决，唯一硬阻断）**

`73b5632` **未触碰** `storage/r2.py`。当前代码逐字为：

```python
return f"{{https://{self._endpoint}}}/{self._bucket}"
```

f-string 中  /  是转义字面量花括号，实际生成：`{https://<endpoint>}/<bucket>`，URL 带字面花括号 → httpx 直接 `InvalidURL`。

**影响面**：`upload/download/delete` 用 `f"{self.base_url}/{key}"`，`list_objects` 用 `f"{self.base_url}?{query}"` —— 即**所有 R2 读写全部失效**。R2 作为独立备份/恢复通道整体不可用。

**修复**：

```python
return f"https://{self._endpoint}/{self._bucket}"
```

（`_sign` SigV4 与 list querystring 逻辑本身已核实正确，仅此一处 URL 拼接错误。）</callout>

## 五、🟠 高危问题（上线前应修）

<callout icon="🟠">**N24-1 · R100「必达/失败重试」保证被提前 `continue` 破坏（静默期追不上）**

`scheduler.replicate_all_active_to_shadows` 中，`new_messages` 依据 **shadow 游标** 计算，随后 `if not new_messages: continue` 在 **R100 复制块之前** 执行。

后果：若某轮 R100 复制曾失败（r100 游标落后），而此后该 Active 频道进入静默（shadow 游标之后无新消息），则 `continue` 会跳过 R100 块，**R100 在静默期永远追不上**，直到有新上传才恢复 —— 违反「所有内容都进 R100 / 复制必须成功、失败下周期重试」的设计承诺。

**修复**：将 R100 追赶逻辑移到 `if not new_messages: continue` **之前**，或对 R100 使用独立游标独立判断（`new_messages_r100 = 从 r100 游标算`），与 shadow 判断解耦。</callout>

<callout icon="🟠">**N24-4 · 影子频道 msg_id 映射缺失时回退成主频道 msg_id，可能投递错文件（本轮 `delivery_resolver.py` 新发现）**

`try_deliver` 在从影子频道发送前调用 `resolve_backup_msg_id(main_msg_id, from_channel_id)` 查 `message_backups` 映射。若映射不存在（该消息尚未复制到此影子频道，例如刚上传或正处于 N24-1 静默追赶缺口），函数**直接返回原始 `main_msg_id`**，随后对影子频道执行 `copy_message(main_msg_id)`。

但各频道的 msg_id 互不相同，用主频道的 msg_id 去影子频道 copy：轻则 `BadRequest`（消息不存在，投递失败），**重则命中影子频道里另一条无关消息 → 投错文件**（数据正确性风险）。

此隐患与 N24-1 叠加：静默追赶缺口期间正是映射最可能缺失的时刻。

**修复建议**：当 `from_channel_id` 是影子/非原始频道且映射缺失时，应判定为「该影子暂无此文件」直接返回失败让环形降级换下一频道，而非回退用原始 msg_id 盲发。</callout>

## 六、🟡 中危 / ℹ️ 提示
