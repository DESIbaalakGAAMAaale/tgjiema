## 二、大改总览

引入 Redis Stream（`dsp_jobs` / 消费组 `dsp_grp`）作为 dsp 派件的**事件驱动通道**，与原 SQLite `dsp_notify` 轮询**并存互补**；`REDIS_URL` 为空或连接失败时**整链降级**到 SQLite 轮询。配套重写了动态限速、FloodWait 退避与按频道限速。

## 三、核心链路逐模块结论

### 1. 生产者路径 ✅ 设计正确

`idx_bot._dispatch_to_dsp → enqueue_job`：

- 先写 SQLite 本地队列（临时负数 `local_id`）+ `notify_dsp_new_job`，**同步返回**用户；CRDB 写入 fire-and-forget。
- 关键点：**不在 enqueue 时用负数 `local_id` 做 `xadd`**，而是在 `_sync_new_job_to_crdb` 拿到真实 `crdb_id` 后再 `xadd_job(crdb_id)`。源码注释明确说明这是为「避免与 `update_local_job_crdb_id` 竞态导致 job 丢失」。这一点是**正确且必要**的设计——曾担心的「新 job 从不进 Stream」的隐患不存在。
- CRDB 写失败（`crdb_id` 保持负数）→ 不 `xadd`，由 dsp 降级轮询 `get_local_pending_jobs` 兜底。降级安全。

### 2. 消费者路径 ✅ 无重复投递

`dsp_bot._dsp_worker`：`xreadgroup_jobs(block=5000, count=10)` → 逐条取 `crdb_id` → `mark_local_job_dispatched`（**CAS：pending→dispatched**，防多 worker 重复认领）→ 发送 → 无论成败 `XACK`（失败由 `_send_one_job` 重新 `xadd` 兜底）。Stream 空则回落 `get_local_pending_jobs(10)`；`redis_messages<10` 时额外补 5 条 SQLite pending。语义自洽，未见重复发送风险。

### 3. 队列原语（cache_store）✅

`insert_local_job`（负数 ID 唯一性自旋）、`mark_local_job_dispatched`（CAS）、`reclaim_stale_dispatched`（600s 回收 dispatched→pending 并返回 id 供重投）、`reactivate_waiting_start_jobs`（/start 后 waiting_start→pending）逻辑均正确，回收/重投都返回 id 交由 dsp 侧 `xadd`。

### 4. CRDB 出队 ✅

`dequeue_jobs`：`CTE + FOR UPDATE SKIP LOCKED + UPDATE ... RETURNING` 单次往返原子出队，`wait_for(timeout=5.0)` 防慢查询卡死。并发认领安全。

### 5. 限速/FloodWait 重构 ✅

`dynamic_rate_limiter`（按 pending 深度在 0.2s~3.0s 间线性调整）、`flood_waiter`（MAX_BACKOFF=120、连续 FloodWait 熔断=10、max_retries=5）、`per_channel_limiter`（15/min）、`rate_limiter`（滑动窗口 + 10min 清理 + 懒加载单例）职责清晰，参数合理。`SEND_CONCURRENCY=25` 信号量约束并发。

### 6. 权限/配额 ✅

`permission.py`：`try_consume_quota` 原子扣减修复了 TOCTOU；失败退款 `refund_quota` 只记日志不抛；合集码「整体扣 1、子码不扣、全失败退款」逻辑与普通码路径一致（blocked/expire 双检）。

### 7. 调度/告警/缓存 ✅

`scheduler.py` 降级两阶段去抖（suspicious→confirm，fail_streak≥3）、环形拓扑校验、manifest 补拷贝（媒体组感知、FloodWait 重试）；`mon_bot` 告警按事件键 600s 冷却、仅在严重度变化时通知、恢复通知；`cache.py` LRU+TTL、请求计数缓冲批量刷写、水位仅在整批成功时推进。均稳健。

## 四、发现的问题（按严重度）

| 编号 | 级别 | 模块 | 问题 | 建议 |
| --- | --- | --- | --- | --- |
| N-R1 | P2 | redis_client / dsp | **Redis PEL 无 XPENDING/XAUTOCLAIM 回收**：worker 在 XREADGROUP 之后、XACK 之前崩溃，会在消费组 PEL 中留下永不确认的孤儿条目。job 本身由 SQLite `reclaim_stale_dispatched`(600s) 兜底重投不丢，但 PEL 随崩溃次数持续膨胀。 | 增加周期性 `XAUTOCLAIM`/`XPENDING` 扫描，认领并处理/丢弃陈旧 PEL 条目后 `XACK`。 |
| N-R2 | P2 | dsp | **消费者名固定 `worker-{0,1}`**：单进程 OK；一旦水平扩容多个 dsp 进程，消费者名会跨进程撞名，导致 PEL 归属混乱。 | 消费者名加入 `hostname+pid`，或明确文档化「dsp 仅单进程」。 |
| N-R3 | P2 | dsp / redis | **持续满载下 MAXLEN 裁剪饥饿**：Stream 上限 10000 近似裁剪；SQLite 兜底只在 `redis_messages<10` 时触发，持续满载（恒为 10）时不会回落轮询，被裁掉但仍 `pending` 的 SQLite job 可能饥饿（`reclaim_stale_dispatched` 只处理 dispatched 不处理 pending）。 | 每 N 轮强制轮询一次 SQLite；或提高 MAXLEN + 增加背压/告警。 |
| N-R4 | P3 | config / mon | `RELAY_SAFE_POOL_SIZE` 在 mon_bot 用 `getattr(默认 2)` 引用，但 `settings.py` 未声明该字段 → 无法经 `.env` 调整。 | 在 `settings.py` 补声明。 |
| N-R5 | P3 | dsp / enqueue | Redis 模式下 worker 不再消费 `dsp_notify`（仅 `not redis` 时 `wait_for_dsp_job`），但 `enqueue_job` 仍写 `dsp_notify`。无害，属冗余写。 | 可在 Redis 可用时跳过 `dsp_notify` 写入，或保留作降级冗余（建议保留）。 |
