## 二、🔴 修复引入的新严重问题

### F-7　Telethon 消息用 `.message_id` 访问 → C1/C2 实际仍失效

`_fetch_new_messages` / `_fetch_all_media` 现在返回的是 **Telethon Message** 对象（消息 ID 属性是 `.id`），但下游仍按 python-telegram-bot 的 `.message_id` 使用：

- `_copy_messages`：`bot_instance.copy_message(..., message_id=msg.message_id)` → 每条抛 `AttributeError`，被 `try/except` 吞掉，`copied=0`；
- `replicate_all_active_to_shadows`：`latest_id = max(msg.message_id for msg in new_messages)` → **未捕获的 AttributeError**，整轮复制直接抛出；
- `auto_fill_new_channels`：`latest_id = max(msg.message_id for msg in all_media)` → 同样抛出。

**后果：** 当 `RELAY_API_ID/HASH` 已配置（即走 Telethon 主路径）时，复制与存量补齐会立即异常中断；只有 Telethon 不可用、回退到 `get_updates`（PTB 消息才有 `.message_id`）时才不崩——而那正是原本被判定「不可靠」的老路径。**等于 C1/C2 名义已修、实际仍未建立冗余。**

> 修法：Telethon 分支统一改用 `msg.id`（Telegram 的 msg_id 在 MTProto 与 Bot API 通用），`_copy_messages` 与两处 `max(...)` 一并改。
> 

### F-9　影子副本未写 `message_backups` 映射 → 故障切换投递仍不可达

`_copy_messages` 调用 `copy_message` 后**丢弃了返回值**（目标频道新生成的 msg_id），也未写入已存在的 `message_backups(main_msg_id, backup_channel_id, backed_msg_id)` 表。而 dsp_bot 故障切换时是用**原始 msg_id** 去投递降级/影子频道（`try_deliver(shadow_channel, 原 msg_id)`）。

由于影子频道里该文件是 `copy_message` 产生的**不同 msg_id**，用原 msg_id 会指向错误或不存在的消息 → 依旧 404 / 投错文件。**即便 F-7 修好，只要没有 msg_id 映射，冗余投递仍不可用。** 与上轮 F-2 / N-M3 同根：需要在复制时持久化 `backed_msg_id`，投递时按目标频道查映射。

## 三、🟠 其他新发现 / 仍未闭环

- **N-H2（中继双实现分叉，仍存在）：** `services/user_relay.py` 的 `UserRelay` 整套仍在，其 `_wait_for_admin_code` 用的是**全局键** `relay_auth_code` / `relay_auth_pending`（无手机号）。本轮把 `/relay_code` 改成 per-phone 后，一旦 `UserRelay.start()` 被调用，它读的全局键无人写入 → 登录必然超时（等于把老 F-5 平移到了 user_relay）。建议删除该文件或与 RelayInstance 统一。
- **F-8（`/relay_pending` 状态永错）：** 该命令读全局 `relay_auth_pending`，但 RelayInstance 现写 per-phone `relay_auth_pending:{phone}` → 无论是否在等码，始终显示「不需要验证码」，管理员无法判断该给哪个号提交。建议改为遍历各手机号键或带手机号参数。
- **F-2（环形降级复用同一 msg_id，未变）：** dsp_bot `_process_single_job` 仍对**同一 msg_id** 沿环重试降级/影子频道；与 F-9 同根因，目前只有 C3「回退原始存储频道」这一腿可靠。
