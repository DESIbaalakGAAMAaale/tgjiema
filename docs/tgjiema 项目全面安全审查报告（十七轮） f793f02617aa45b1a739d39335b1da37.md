# tgjiema 项目全面安全审查报告（十七轮）

<aside>
📌

审查对象：GitHub 仓库 `maxiuquan/tgjiema`（默认分支 `master`，最后提交 2026-07-03）。主语言 Python 91.6%。本报告基于对仓库源码与设计文档的逐文件通读，围绕**文件安全性、代码可靠性、数据安全性**三大维度，分十七轮呈现。每条问题标注严重度：🔴严重 / 🟠高 / 🟡中 / 🟢低 / ℹ️提示。

## 概览

**项目定位**：一个基于 Telegram 的「文件寄存 / 取件码」系统。5 个账号 × 9 频道组成「环形冗余 v2」存储拓扑，由 5 个 Bot（Up 上传 / Idx 解码索引 / Dsp 派送 / Mon 监控 / Admin 管理）+ FastAPI Web 后台 + CockroachDB(CRDB) 云库 + 本地 SQLite 缓存 + Cloudflare R2 备份 + CF Workers 引导 Bot 构成。核心思路：**读写优先走本地 SQLite，异步批量回写 CRDB**，以压低 CRDB 的 RU 消耗。

**总体评价**：架构设计有明显的工程化思考（环形降级、SQLite-First 降本、死信队列、CSRF/登录限流、Fernet 加密），并且已经历多轮内部复查（仓库 `docs/` 内含第 12、13 轮复查与一份 7.5 万字的全面审查报告）。但仍存在若干**真实的可靠性与数据安全隐患**，且仓库内的 `TODO_FIXES.md` 已明显过期（部分"高危"项实际已修复或本就是误报，详见第十七轮）。

## 第一轮 · 架构与整体设计

**审查文件**：`ARCH_OVERVIEW.md`、`run_all.py`、`docker-compose.yml`、`deploy_vps*.sh`

- ℹ️ 环形冗余拓扑（15 组 × 3 槽 + R100 兜底）设计清晰，单账号被封时每组仍存活 ≥2 频道，无单点。文档质量高。
- 🟡 **多进程 + 本地缓存的一致性是全系统最大的架构性风险**。5 个 Bot 是各自独立的 systemd 进程，各持一份 L1 内存缓存 + 本地 SQLite，仅靠 TTL / 轮询同步。Mon 切换频道后，其它进程最长 ~60s 才感知，窗口期内 Up/Dsp 可能仍读写旧频道 → 消息写入/投递到错误频道。（详见第十三轮）
- 🟡 跨进程「唯一真相源」不统一：同一份数据分布在 CRDB、多个 SQLite 文件、多个内存字典中，双写 + 异步回写在崩溃/竞态下存在收敛风险。
- 🟢 `run_all.py --standalone <bot>` 单进程单 Bot 的部署模型清楚，systemd 拆分利于单点重启。

## 第二轮 · 配置与密钥管理

**审查文件**：`config/settings.py`、`.env.example`

- 🟢 `settings.py` 用 pydantic `model_validator` 做了扎实的启动期校验：强制 5 个 Token + CRDB URL；强制 `RELAY_ENCRYPTION_KEY` 存在且为合法 44 字符 Fernet 密钥；拒绝 `ADMIN_PASSWORD` 为空或默认 `CHANGE_ME_NOW`；非本地监听时强制密码 ≥12 位。这些是很好的"安全左移"。
- 🟠 **所有敏感凭证以明文存放于 VPS 的 `.env`**（5 个 Bot Token、CRDB 连接串含库密码、R2 密钥、`RELAY_API_HASH`、`RELAY_ENCRYPTION_KEY`）。这被 `TODO_FIXES.md` 列为"已接受风险"，但仍应：`chmod 600 .env`、限制 `data/` 目录权限、考虑用 systemd `EnvironmentFile` + 受限权限或密钥管理服务。（部署脚本目前未对 `.env` 设权限，见第十四轮）
- 🟡 `RELAY_ENCRYPTION_KEY` 与被它加密的 SQLite 库 (`data/relay_pool.db`) **同机同目录**存放。一旦 VPS 被攻破，密钥与密文同时泄露，加密的实际防护价值被大幅削弱（仅能防"裸库文件外泄"）。
- 🟢 `get_accounts_config()` 对非法频道 ID 做了 `try/except` 跳过并告警，健壮。

## 第三轮 · Web 后台认证与访问控制

**审查文件**：`admin/__init__.py`

- 🟢 用户名/密码用 `secrets.compare_digest` 常量时间比较，防时序攻击；登录失败限流（5 分钟 5 次/IP）；CSRF token 按 username 精确绑定、`httponly + samesite=strict` cookie、`secrets.token_hex(32)`。整体优于多数同类项目。
- 🟠 **HTTP Basic Auth 无内建 TLS**。凭证在每个请求头中传输；文档/部署未提供反向代理 + HTTPS 指引。默认 `ADMIN_WEB_HOST=127.0.0.1` 缓解了直接暴露，但一旦对外必须叠加 TLS，否则凭证明文过网。
- 🟠 **登录限流以 `request.client.host` 为准，未处理反向代理**。若置于 Nginx/Cloudflare 之后，所有请求源 IP 变为代理 IP：要么全局互相干扰被误锁，要么攻击者真实 IP 无法被限流。应在受信代理下解析 `X-Forwarded-For`。
- 🟡 Basic Auth 无"会话/登出"概念，浏览器缓存凭证；`_csrf_tokens` 以明文 JSON 持久化到 SQLite（同机风险等级同上）。
- 🟢 所有写操作（改会员、封禁、删文件）均校验 CSRF + 校验合法枚举值，良好。

## 第四轮 · 数据安全与加密（中继凭证 / R2）

**审查文件**：`database/relay_db.py`、`storage/r2.py`

- 🟢 `relay_db.py` 的 Fernet 加密层（PRE-10）设计正确：`encrypt/decrypt` 在库缺失、密钥缺失、格式非法、解密失败时**一律抛 `RuntimeError`，绝不静默回退明文**。这修复了 `TODO_FIXES.md` #11 所述隐患。
- 🔴 **本地加密、云端明文：不一致的关键漏洞**。`add_account/update_account` 本地入库时 `encrypt(api_hash)`，但随即 `asyncio.create_task(_sync_relay_to_crdb(api_id, api_hash, phone))` 把**原始明文 `api_hash`** 同步到 CRDB；且 CRDB `relay_accounts.api_hash` 为普通 `TEXT`。结果：本地 SQLite 是密文，**云端 CockroachDB 却存明文 `api_hash`**。这使本地加密形同虚设（云库一旦泄露即全部暴露），且启动时从 CRDB 恢复的账号会把明文再 `encrypt` 入本地——数据语义也不统一。**建议：入云前同样加密，或云端不存该字段。**
- 🟡 `get_bot_cooldown` 内使用 `datetime.now(datetime.timezone.utc)`，但文件顶部 `from datetime import datetime`，`datetime.timezone` 属性链在该 import 形式下会 `AttributeError`（应为 `from datetime import timezone` 或 `datetime.now(timezone.utc)`）。该异常被外层 `try/except (ValueError, TypeError)` **捕获不到**（是 AttributeError），冷却检查可能抛错。需核实调用路径。
- 🟡 `r2.py` 的 `list_objects` 签名不一致：`canonical_uri = "/"+bucket+"/"+key`，但列举时把整个 `?list-type=2&prefix=` 当作 `key` 传入，导致规范请求与实际 URL 不匹配 → 列举/恢复备份可能签名失败。上传/下载/删除路径的签名是一致的。
- 🟢 R2 用标准 AWS SigV4 自实现，`UNSIGNED-PAYLOAD`，无第三方 SDK，依赖面小。

## 第五轮 · 数据库层与 SQL 注入

**审查文件**：`database/session.py`（`CockroachDBClient` / `D1Collection`）

- 🟢 **SQL 注入防护到位**：所有查询走 asyncpg 的 `$1,$2` 占位参数化；`_validate_identifier` 用 `^[a-zA-Z_][a-zA-Z0-9_]*$` 白名单校验列名/表名；`_escape_like` 转义 `% _ \`。这是全项目值得肯定的安全点。
- 🟠 存在 `execute_raw(sql, params)` 公开原始 SQL 通道（供 CASE WHEN 批量更新）。目前调用方拼接的是代码常量列名，风险可控，但这是一个需要长期守护的"后门"——**任何未来把用户输入拼进 `execute_raw` 的改动都会引入注入**。建议在此处加注释红线 + 代码评审规则。
- 🟡 DDL/迁移逻辑：`MIGRATION_STATEMENTS` 里少数 `ALTER TABLE ... ADD COLUMN`（无 IF NOT EXISTS）依赖 `try/except` + 字符串匹配 `"already exists"/"duplicate"` 来吞错。字符串匹配依赖 CRDB 错误文案，跨版本可能不稳，导致误抛或误吞。
- 🟡 `_row_to_dict` 对 JSON 字段解析失败时静默回退为原值/空，可能掩盖脏数据。
- 🟢 连接池 `min=1,max=5,statement_cache_size=256`，事务用 `async with conn.transaction()`，基本规范。

## 第六轮 · 文件访问控制与解码鉴权

**审查文件**：`bots/idx_bot.py`、`services/permission.py`

- 🟢 解码链路的访问控制层次合理：`check_decode_permission` → 封禁校验 → 配额校验 → `status==active` → `code_entry offline` → 过期校验；`idx_bot` 再叠加 `status==detached` 拦截与 `blocked_users` 名单拦截（举报人黑名单），且对不存在一律回"文件不存在或已被删除"，不泄露存在性差异。
- ℹ️ **设计上取件码是"持有即可取"的可分享凭证**（无按用户绑定），这是产品定位使然，非漏洞；但意味着码一旦外泄即等于文件外泄。
- 🟡 内部码识别用 `re.search(r'(prefix\S+)', raw_text)`——"只要出现前缀，后面无论是什么都当内部码"。过于宽松，配合 `check_code_expired` 里对 `expire_time` 字符串解析的多分支，建议对提取到的码再跑一次 `is_valid_code_format` 严格校验，避免畸形码进入后续查询。
- 🟡 配额"投递成功后才递增"的设计（避免失败扣额）是对的，但递增与投递之间没有幂等键：投递成功、递增前进程崩溃 → 该次不计费（对运营轻微不利，可接受）。
- 🟢 强制关注频道 `check_force_join` 在各入口统一前置校验。

## 第七轮 · 取件码生成与可预测性

**审查文件**：`services/code_generator.py`

- 🟠 **码的"随机"实为确定性派生**：`_generate_deterministic_id` = `SHA256(time_ns + pid)` 映射到 36 进制 12 位。作者依赖 SHA256 雪崩效应使其"不可猜测"。空间 36¹² ≈ 4.7×10¹⁸，枚举不可行——**抗枚举足够**。但严格意义上它**不是密码学随机**：种子熵仅来自纳秒时间戳 + PID，理论上在已知进程 PID、可估算时间窗口时，攻击面小于真随机。**建议直接用 `secrets.token_hex`/`os.urandom` 取随机部分**，成本几乎为零，彻底消除可预测性质疑。
- 🟢 `is_valid_code_format` 用严格正则区分内部/外部码，避免把普通文本误判为码。
- 🟡 `generate_unique_code` 注释说"碰撞靠 DB 主键兜底"，但 `idx_bot` 生成后若主键冲突未见重试逻辑（需确认），极低概率下会导致该次上传失败而非重生成。

## 第八轮 · 上传流程可靠性

**审查文件**：`bots/up_bot.py`

- 🟢 已加入 `_cleanup_pending` 后台任务，按 30s / 120s 清理超时 media group 与 external buffer（修复了 `TODO_FIXES.md` #10 的内存泄漏）；PRE-13 让 `end_upload` 只 flush 本人媒体组；PRE-14 校验存储频道/消息 ID 非零。这些是实打实的加固。
- 🟢 **`TODO_FIXES.md` #4（`_json_dumps` 必崩 `UnboundLocalError`）是误报**：海象运算符 `result := json.dumps(...)` 会**无条件**先赋值 `result` 再判断 `isinstance`，故末尾 `return result` 恒有定义。此"P0 必崩"实际不成立（详见第十七轮复核）。
- 🟡 `_active_slot_index` 轮转虽有 `_pending_lock` 保护，但 `_active_a_slots` 的刷新与读取跨协程，槽位列表在刷新瞬间可能为旧值，属第一轮所述一致性问题的局部体现。
- 🟡 多处 `except Exception: pass` / `except Exception: logger...` 后仍继续，个别失败路径（如复制到频道失败）会让用户以为已接收但实际丢件（media group 并发复制中部分失败仅提示"失败 N 个"）。

## 第九轮 · 解码/索引处理管线

**审查文件**：`bots/idx_bot.py`（poll / pending / external）

- 🔴 **`_process_pending_uploads` 竞态（`TODO_FIXES.md` #2，仍未见修复）**：查询 `processed=0` 与标记 `processed=1` 之间无原子锁 / `SELECT ... FOR UPDATE`。多 worker 或重启重入时，**同一 pending 记录可能被重复处理 → 生成重复 code / 重复给用户发码**。建议用 `UPDATE pending_uploads SET processed=1 WHERE id=$1 AND processed=0 RETURNING ...` 的 CAS 语义认领。
- 🟡 外部码链路（`handle_external_code`）分支多、`return` 点多，多处 `from services.permission import increment_user_quota_used` 局部 import；异常路径下"已发外部请求但 idx 侧异常"可能导致配额与实际投递不一致。
- 🟡 `handle_external_code` 中对 `msg_ids = [int(mid) for ...]`，若 `batch_msg_ids` 脏数据可能得到空列表后回退 `primary_channel_msg_id`，需保证其非空（PRE-14 在上传侧已加固）。

## 第十轮 · 派送/投递可靠性

**审查文件**：`bots/dsp_bot.py`、`database/session.py`（`dequeue_jobs`）

- 🟢 投递健壮性较强：`copy_message` 跨 Bot 复制（file_id 跨 Bot 不可用，路径选择正确）；单条失败后沿环最多试 10 个降级槽位，再兜底原始存储频道；媒体组失败回退逐条发送；死信队列（`retry_count>=3` 标 `dead`）+ semaphore 并发控制 + 动态限速。
- 🟠 **`dequeue_jobs` 原子性边界（`TODO_FIXES.md` #13）**：虽用 CTE + `UPDATE ... RETURNING` 保证单次出队原子，但 5s 超时重试与原操作隔离不清，极端情况下**同一 job 可能被两个 worker 认领 → 同一文件重复投递给用户**。建议给 `jobs` 加 `worker_id`，`WHERE status='pending'` CAS 认领。
- 🟡 `_fallback_single_send` 恒 `return True`（即便逐条全失败也返回 True），调用方据此判断"成功"会误判——与 `TODO_FIXES.md` #5"返回值语义不一致"同源，需统一。
- 🟢 `_send_semaphore` 双重获取死锁已在注释中规避（fallback 不再二次获取），说明作者已踩过坑。

## 第十一轮 · 监控、降级与自动补齐

**审查文件**：`services/mon/scheduler.py`

- 🟢 **`TODO_FIXES.md` #3（`_is_channel_nearly_empty`/`_fetch_all_media` 是死代码）已修复**：现二者用 Telethon `iter_messages` 真实实现，`_fetch_all_media` 还做了分页拉全量历史（N-16-3）。auto-fill 已可用。

## 第十二轮 · 中继账号池与外部码安全

**审查文件**：`services/relay_instance.py`、`services/relay_pool.py`、`database/relay_db.py`

- 🟠 中继使用**真实 Telegram 用户账号**（api_id/api_hash/手机号登录）去解外部码，属于"用户账号自动化"，有**被 Telegram 判定为滥用/封号**的合规与稳定性风险；账号被封会连锁影响外部码功能。
- 🟠 承接第四轮：中继账号最敏感的 `api_hash` **在云端明文**，是数据安全的重点整改项。
- 🟢 `relay_pool` 负载均衡权重（等待时长/今日请求/间隔）可配置，`record_request` 用 `INSERT ... ON CONFLICT DO UPDATE` 原子累计，避免竞态。
- 🟡 `relay_log` 记录 `code`、`bot_target` 等，可能含用户取件行为，注意日志留存与隐私。

## 第十三轮 · 缓存一致性与多进程模型

**审查文件**：`database/cache.py`、`database/cache_store.py`（75KB，核心）、`database/session.py`

- 🟠 **多进程缓存一致性（`TODO_FIXES.md` #12，需架构级处理）**：Mon 改拓扑后其它进程最长 60s 才刷新，窗口期消息可能写/发到旧频道。建议：CRDB `LISTEN/NOTIFY` 广播失效，或热点（cells 拓扑）TTL 降到 5–10s，或读取时校验 `updated_at` staleness。
- 🟡 SQLite-First 全表 bootstrap（启动时把 users/codes/file_records/external_code_mapping 全量灌入本地）在数据量增长后会拉长启动时间与占用磁盘；需评估上限与增量策略。
- 🟡 `TODO_FIXES.md` #8 称 `database/cache.py` 有错误 import 路径 `from utils.config import settings`，需实测确认是否已修正为 `config.settings`（若未修，缓存模块加载即失败——但项目能运行说明大概率已修，属文档过期）。
- 🟢 SQLite 均开启 WAL + busy_timeout + 周期 checkpoint，本地并发读写配置合理。

## 第十四轮 · 部署、依赖与运行时安全

**审查文件**：`deploy_vps_per_bot.sh`、`deploy_vps.sh`、`docker-compose.yml`、`Dockerfile`、`requirements.txt`

- 🟠 **所有 systemd 服务 `User=root` 运行**。虽设了 `NoNewPrivileges=true`、`PrivateTmp=true`，但以 root 跑网络服务是过度授权。建议创建专用非特权用户（如 `tgjiema`），并把 `WorkingDirectory`、`data/` 归其所有。
- 🟠 **部署脚本未收紧 `.env` 权限**：`cp .env.example .env` 后直接 `nano`，未 `chmod 600`。含全部明文密钥的文件默认权限可能被同机其它用户读取。应加 `chmod 600 .env` 并 `chmod 700 data/`。
- 🟡 `pip install` 未使用哈希锁定（无 `requirements.lock`/`--require-hashes`），供应链可复现性与防篡改弱；`requirements.txt` 建议锁定精确版本。
- 🟢 systemd 内建重启防抖（`StartLimitBurst=5 / Interval=60`）、优雅关闭（`SIGINT`+`TimeoutStopSec`）、`LimitNOFILE` 合理。
- ℹ️ 需确认 `.gitignore` 覆盖 `.env`、`data/*.db`、session 文件（Telethon `.session` 含账号登录态，绝不可入库）。

## 第十五轮 · Web 前端与注入（XSS/模板）

**审查文件**：`admin/templates/*.html`

- 🟢 使用 FastAPI `Jinja2Templates`，`.html` 默认**开启自动转义**；`users.html` 中  `user.username` 、`file_code` 等均经转义渲染，未见 `|safe`，**无明显存储型 XSS**。用户名/文件码等不可信数据渲染是安全的。
- 🟡 搜索参数 `search` 直接进 CRDB `$regex`（`admin/__init__.py`），虽走 Mongo 风格 regex 而非拼 SQL，但**用户可控 regex 存在 ReDoS 风险**（构造灾难性回溯的正则拖垮查询）。建议对 search 做长度限制 + 转义为字面量（`re.escape` 语义）而非原样当 regex。
- 🟢 CSRF token 注入模板 + cookie 双提交校验，前端表单均带 `csrf_token`。

## 第十六轮 · 错误处理、日志与可观测性

**审查文件**：全局 `logger` 使用、`utils/monitor.py`、`utils/flood_waiter.py`

- 🟡 **大量 `except Exception: pass` 静默吞异常**（admin 状态持久化、通知、消息编辑等）。可用性上是"不让边缘失败拖垮主流程"，但会**掩盖真实故障**、增加排障难度。建议至少 `logger.debug/warning` 记录。
- 🟡 日志中可能出现 `user_id`、`file_code`、`phone`、外部 `bot_target` 等准 PII / 敏感取件信息（`LOG_LEVEL=INFO` 默认）。建议对手机号、码做脱敏，并明确日志留存策略。
- 🟢 有集中式 `metrics`（发送成功/失败、备份计数、各 Bot 处理/错误数）+ `/health` 无鉴权健康检查（读共享心跳表，关键 Bot 掉线返回 503），可观测性基础良好。
