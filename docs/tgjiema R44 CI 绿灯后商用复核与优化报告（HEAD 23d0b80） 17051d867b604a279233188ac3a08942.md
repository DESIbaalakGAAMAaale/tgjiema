## 4. 生产 GO 前剩余阻断门禁

### G0-1 · Branch protection 尚未验证

Actions 全绿不代表可以绕过检查直接 push/merge。必须证明：

- main/master required checks 包含 CI 与 Release Gates；
- strict up-to-date checks；
- 至少 1 个 review；
- enforce admins；
- 禁止 force push/delete；
- 发布只能从受保护 tag/commit 产生。

### G0-2 · 外部副作用仍不能仅凭数据库幂等状态证明 exactly-once

ApprovalExecutor 已 claim `command_executions`，但 handler 执行与 Telegram/R2/CRDB 等外部动作无法和 SQLite 原子提交。若外部动作成功后进程崩溃、lease 过期后重试，仍可能重复。

**最终方案**：

- 每个外部副作用必须持久化 `effect_receipts(action_id,effect_type,target,status,external_id)`；
- handler 执行前检查 receipt；
- 外部系统支持幂等 key 时传 action_id；
- 不支持时使用对账/查询确认，语义明确为 effectively-once；
- restore/takedown/ban/purge 在副作用后、状态写前执行 kill -9 测试。

### G0-3 · 生产恢复审批不能只检查非零 ID

BackupEngine 的生产恢复必须验证真实 `approval_id/action_id/request_hash/status=EXECUTING`，并由 ApprovalExecutor 内部调用。公共函数不得接受任意非零 approver_id 直接恢复。

### G0-4 · Admin bootstrap/Session/MFA 需真实浏览器验证

源码已有 bootstrap/readiness、Session/MFA，但还需证明：

- 首次 bootstrap 生成稳定 principal 并授予 super_admin；
- 未 bootstrap 时 Web 拒绝启动；
- 登录、MFA、过期、撤销、logout、break-glass、CSRF、HTTPS 代理全部正常；
- 所有管理路由统一使用 async session + RBAC/CommandBus。

### G0-5 · 全新机恢复与 RU 仍无环境级证据

CI restore drill 主要验证代码/模拟环境，不能代替：

- CRDB 托管备份 + 加密 R2 bundle + SQLite/Relay session/DLQ 在新机恢复；
- Telegram 副本抽样可取；
- RTO≤30 分钟；
- 72 小时官方 Cloud RU 空载数据。

## 7. CRDB RU 最终优化与验证

### 7.1 目标架构

```
Bot/Admin/Writer
  → SQLite transaction + dirty_outbox
  → 无 CRDB URL/SDK

crdb_sync
  → Redis leader lease
  → dirty>0 才 lazy-connect
  → 合并最高 version
  → 100–500 行批量 UPSERT/soft-tombstone
  → 空闲 5 分钟关闭 pool
```

### 7.2 剩余优化

- tombstone 优先同步 deleted_at/version，不立即物理 DELETE；
- version 必须由 SQLite 表原子递增，不能默认 0；
- local_only 表不写 dirty_outbox；
- RU collector 失败输出 unknown + freshness；
- migration、backup、restore RU 单独统计，不混入业务空载。

### 7.3 验收

- 业务角色 `0 RU/天`；
- 总空载理想 `≤20 RU/天`，硬上限 `≤100 RU/天`；
- 连续 72 小时从 CockroachDB Cloud 官方 Metrics 导出按 application_name 的报告；
- 超过 100 预警，超过 500 阻断发布。
