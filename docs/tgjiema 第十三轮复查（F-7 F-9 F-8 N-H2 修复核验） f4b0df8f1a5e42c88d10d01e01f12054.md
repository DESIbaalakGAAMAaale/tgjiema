## 三、本轮新发现的小问题（低危 / 质量）

- **N-13-1（低危）**：`scheduler._write_backup_mappings` 直接用 `col.insert_one(...)` 写映射，而 `database/session.py` 已提供带 upsert 语义的 `save_message_backup()`。同一 `(main_msg_id, backup_channel_id)` 若被重复复制会命中主键冲突（当前靠逐条 `try/except` 吞掉，不致命，但会丢日志噪音、且无法更新 `backed_msg_id`）。建议改用 `save_message_backup()` 以获得幂等 upsert。
- **N-13-2（质量）**：`services/user_relay.py` 的 `UserRelay` 整个类仍然保留，但运行时中继实际走 `relay_pool` / `RelayInstance`（`is_ready`/`relay_user_id` 都委托给 pool）。键错配虽已修好，但该类属于**未被主流程调用的重复实现**，建议删除或与 `RelayInstance` 合并，避免后续再次分叉。
- **N-13-3（提示）**：`resolve_backup_msg_id` 对所有异常静默 `pass` 并回退到原始 `main_msg_id`。正常路径没问题，但当 `message_backups` 查询因 DB 抖动失败时会“悄悄”退回可能 404 的原始 msg_id，排障时无日志线索。可考虑加一条 `debug` 级日志。

## 四、优先级建议

1. **H2（🟠，唯一未闭环项）**：将 `_login_failures` / `_csrf_tokens` / `_count_cache` 迁移到共享存储（如 SQLite `cache_store` 或 CRDB），使限流与 CSRF 状态跨进程重启/多 worker 保持一致。
2. **N-13-1**：`_write_backup_mappings` 改调 `save_message_backup()`（幂等 upsert）。
3. **N-13-2**：删除或合并 `user_relay.py` 中已废弃的 `UserRelay` 类。
4. **N-13-3**：给 `resolve_backup_msg_id` 的异常分支补一条 debug 日志。
